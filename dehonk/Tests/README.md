# De-Honk tests and render harness

This folder holds the offline harness for the De-Honk DSP core described in `dehonk/SPEC.md` (sections 7 and 8). It builds three programs from the same source as the plug-in's core, `dehonk/dsp/`, with no JUCE dependency: `dehonk_render`, which runs a WAV file through the core and reports what it did, `dehonk_tests`, which runs the tests from sections 7 and 13 of the spec on signals it generates itself, and `dehonk_dialogue` and `dehonk_realmix`, which measure the dialogue sidechain, Snap and Compare on a real mix and its dialogue stem. A small script, `run_corpus.py`, renders a whole folder of session audio in one go, and more in `tools/` find impacts in a mix, measure the section 13 figures on a folder of real mixes and run `dehonk_dialogue` over the library.

Controls are called here by the names the window gives them: Delta, Compare, Attack and Focus are the core's and the tools' `soloHonk`, `diff`, `speed` (0 slow to 1 fast) and `sharpness`, and the test names keep the older words.

## Building

You need CMake 3.22 or newer and a C++20 compiler. From the repository root:

```
cmake -S dehonk/Tests -B dehonk/Tests/build
cmake --build dehonk/Tests/build -j 8
```

The build is Release with full optimisation unless you ask for another build type, and should finish with no warnings (`-Wall -Wextra -Wpedantic -Wshadow -Wconversion`, or `/W4` with MSVC). Every `.cpp` file in `dehonk/dsp/` is compiled into the core. To run the same harness on another implementation of `DeHonkCore.h`, such as a prototype kept outside the repository, point `DEHONK_DSP_DIR` at its folder: `cmake -S dehonk/Tests -B /some/other/build -DDEHONK_DSP_DIR=/path/to/core`.

### Proving the output unchanged

Two tests render a fixed set of cases (`src/GoldenCases.h`: eleven settings, among them Snap, Link, lookahead changes, automation, a sidechain, NaN and infinity in the input), hash every output sample and display frame, and compare the hashes bit for bit with files kept in `golden/`, one set per architecture (arm64 and x86_64). A missing file, or a case missing from one, fails the test.

`golden_mono_stereo` runs the cases at the settings that stand for how the core was before Max Cut, Release and Impact Guard became controls: Max Cut 8 dB (the ceiling used to be fixed there), the release the Speed control used to set along with the attack (300 ms at Speed 0 down to 50 ms at Speed 100%), Impact Guard 0, and the notch movement as it was (`Tuning::handOver` off: the old hand-over, the Threshold inside the release, a notch held up by its slow average). No control reaches that last one: the old sound cannot be set from the window, and the switch is kept in the core for this proof only. At those settings the core must give exactly what the older cores gave. Nothing in these cases engages Diff, and the offset Diff reports (`DisplayFrame::diffOffsetDb`) is not in their hashes: how Diff is switched and how its level match is averaged changed on purpose on 18 November 2026 (SPEC 13.17), so those two things cannot be compared with a core from before. The two files were recorded again that day from the same two old cores with the cases as they are now (`tools/record_references.sh <build folder> <architecture>`), after checking that those cores, built with the cases as they were, still gave the files as they were (72 of 72 on each architecture). Everything else is compared as before:

- mono and stereo at 44.1, 48 and 96 kHz against `golden/golden_ref_<architecture>.txt`, the hashes of the core as it was before surround support. Each case also runs a second time prepared with the layouts the plug-in passes (a centre speaker for mono, left and right fronts for stereo), which must give the same hash.
- 5.1 and 7.1.4 (eleven settings at 48 kHz, three at 44.1 and 96 kHz) against `golden/golden_surround_<architecture>.txt`, the hashes of the core as it was before the three controls.

`golden_defaults` runs the same cases at the plug-in's defaults (Max Cut 6 dB, Release 400 ms, Impact Guard 100%), mono, stereo, 5.1 and 7.1.4, against `golden/golden_defaults_<architecture>.txt`, with three more cases that make the three controls work (a Threshold low enough that the cut is deep for most of the render; and a tone strong enough to reach Max Cut with a broadband burst every 0.9 s, linked and unlinked), with 4 s at 96 kHz as at the other rates, with the guard's reading in the hash, and with Compare: a case that plays in Compare, one whose automation switches it, and the offset Compare reports in every frame. Before comparing, the test checks that the cases do something: every "defaults", "key" and extra render cuts at least half a dB, and the extra ones reach Max Cut and bring the guard fully up. Those hashes were recorded from the current core on purpose (18 November 2026, with the dialogue sidechain, each range's own timing, the link modes and Diff's cross-fade in it). They say nothing about how it should sound, only that it has not changed since; when a change to the sound is meant, record them again.

To record a reference on purpose, copy a core into the build folder and run CMake again: as `ref-dsp/` for a core from before surround (built as `dehonk_golden_ref`, which writes `golden_ref.txt`), or as `ref-dsp2/` for a core with layouts (built as `dehonk_golden_ref2`, which writes `golden_ref2.txt` with the surround cases after the mono and stereo ones).

A third copy, `ref-dsp3/`, is the core as it was before the dialogue sidechain, each range's own timing and the link modes (built as `dehonk_golden_ref3`). No file is kept from it. With those three at their defaults the current core must give what it gave, and that is checked by running the two tools with the same arguments and comparing the files:

```
for a in "--surround" "--compat --surround" "--defaults-no-diff"; do
  dehonk/Tests/build/dehonk_golden_ref3 $a /tmp/ref.txt && dehonk/Tests/build/dehonk_golden $a /tmp/now.txt && diff /tmp/ref.txt /tmp/now.txt
done
```

(with `zsh`, write `${=a}` for `$a`). That is 100 renders at the core's defaults, 100 at the settings of `golden_mono_stereo` and 124 at the plug-in's defaults with the extra cases and the guard's reading: mono, stereo, 5.1 and 7.1.4, among them Link at 0, 30, 50 and 100% and swept. On 18 November 2026 all 324 were the same on arm64 and on x86_64.

A fourth, `ref-dsp4/`, is the core as it was before Detection (SPEC 13.19), built as `dehonk_golden_ref4`. At Detection Fast (the default) the current core must give what it gave, checked the same way with the same three sets of arguments (the cases leave Detection at its default, so they run at Fast). On 18 November 2026 all 324 were the same on arm64 and on x86_64. The same day Diff's level match changed (13.19), so `--defaults` with Diff in it no longer matches that core and `golden_defaults_*` was recorded again.

```
cp -R dehonk/dsp dehonk/Tests/build/ref-dsp2
cmake -S dehonk/Tests -B dehonk/Tests/build && cmake --build dehonk/Tests/build -j 8
```

Put the hashes under the comment header of the file in `golden/` for that architecture. `dehonk_golden out.txt` writes the mono and stereo hashes of the current core at its defaults, `dehonk_golden --surround out.txt` adds the surround cases, `--compat` runs either at the settings of `golden_mono_stereo`, and `dehonk_golden --defaults out.txt` writes the content of `golden_defaults_<architecture>.txt` (the current core only: the extra cases, the guard's reading and Compare). `--defaults-no-diff` is the same without Compare, for comparing with a core from before its cross-fade. For the other architecture on an Apple silicon Mac, configure a second build folder with `-DCMAKE_OSX_ARCHITECTURES=x86_64`.

Bit-identity holds for the compiler and flags it was checked with. How the compiler vectorises a running sum changes its rounding, so code around the core's level-match sums has to be left as it is (there is a comment there).

Both programs set flush-to-zero on their thread before processing, as the plug-in does through JUCE. Pass `--no-ftz` to either of them to see how the core behaves without it.

## Running the tests

`dehonk/Tests/build/dehonk_tests` runs every test and prints each check as it goes, then a summary with one line per test. The exit code is 1 if any test failed. `--list` prints the test names, `--only name` (or a comma-separated list) runs just those, and `--report out.md` also writes the results as a Markdown file that can be pasted into a pull request. A full run takes about three and a half minutes on the development Mac, most of it in the two CPU benchmarks.

`--set name=value` (repeatable) changes one of the core's tuning constants, by its name in `dehonk::Tuning`, for every render in the run that does not set its own tuning. It is there to check that a test can fail: run it against a deliberately wrong setting and it should. For example `--only snap_leaves_hits_alone --set clickNeighbourDb=-100` makes Snap ignore the bands either side, so it takes drum hits for clicks, and the test fails. The summary line names the changed constants.

The CPU benchmark fails the run when the average load misses the targets in section 6 of the spec, or when silence or denormal-level input costs more than signal. Timings depend on the machine and on what else it is doing, so run it on a quiet machine before reading much into a failure. The rule that no block may take more than twice the average is reported but only checked with `--strict-cpu`, because a single interruption by the operating system breaks it; the 99.9th percentile is printed beside the worst block for that reason.

The plug-in's own processor (the JUCE side) has a separate check, `host/HostCheck.cpp`, built from the plug-in's CMake project rather than this one: `cmake --build dehonk/build --config Release --target DeHonkHostCheck`, then run `dehonk/build/DeHonkHostCheck_artefacts/DeHonkHostCheck`. It checks which channel layouts are accepted and refused, that the LFE of every layout comes out bit for bit, odd buffers (no samples, more or fewer channels than the bus, block sizes of 1 and 4096, the host's bypass), a layout change with and without `prepareToPlay`, and the stem formats the JUCE AAX wrapper would offer Pro Tools. For the dialogue sidechain it checks that every layout is taken with the sidechain off, mono or stereo and with nothing else, that the second input bus is mono by default and may be switched off (which is what makes the AAX wrapper offer Pro Tools a key input), that the key's channels, which come after the main ones in the buffer, are never written, and that with the mix itself as the key nothing is cut. It restores a state built by hand as the first test build's were (Link as a percentage becomes Linked from 50% up and Unlinked below, and what that state does not have comes back at its default), and then seven states that the first test build itself saved, kept in `host/FirstBuildStates.h`: one on each of its factory presets, one on its "User preset" entry and one with settings moved. And it checks that every parameter of the first test build is still there with version hint 1 and that everything added since has a higher one, which is what keeps their places in the order an AU host numbers them by.

Scratch files (the `wav_io` round trip) are written in a folder next to the `dehonk_tests` executable, normally the build folder, and removed afterwards.

`--write-signals DIR` writes the generated test signals (the bass-heavy bed with peaks at 151 and 247 Hz, the same bed on its own, peaks at 500 and 900 Hz, the dense twelve-peak signal, pink noise, the sweep, the bass tones, the music-like signal, 2.5 kHz clicks over pink noise, broadband hits over pink noise, the ten impacts over a bed from `impacts_keep_body_tail_front` and the 80 to 600 Hz noise from `noise_is_left_alone`) as WAV files in a mix of formats, for listening or for feeding to `dehonk_render`.

All signals come from fixed seeds with the harness's own random generator, so two runs on any machine use the same audio.

## Rendering a file

```
dehonk/Tests/build/dehonk_render in.wav out.wav [options]
```

The input can have 1 to 12 channels, 16, 24 or 32-bit PCM or 32 or 64-bit float, including files written with WAVE_FORMAT_EXTENSIBLE. It is processed at its own sample rate and the output is written as 32-bit float with the core's latency removed, so it lines up with the input sample for sample.

Every field of the core's parameters has an option: `--depth`, `--sharpness`, `--speed`, `--link`, `--mix`, `--impact-guard` and `--dialogue-amount` take 0 to 1; `--link-mode` takes `linked`, `grouped` or `unlinked` (`--link` is how far a channel follows what it shares, which no control of the plug-in sets to anything but 1); `--detection` takes `fast` or `steady`; `--range-timing fog=20,800` unlocks a range's timing with its own attack and release in milliseconds (`woof`, `tub`, `fog` or `bark`; repeatable); `--key stem.wav` is a sidechain, in time with the input, and `--dialogue 1` takes it as the dialogue stem; `--release` takes milliseconds (50 to 1500) and `--max-cut` dB (3 to 12); `--woof`, `--tub`, `--fog` and `--bark` take 0 or 1 and switch the four notch modules (Tub and Fog are on by default); `--snap` takes 0 or 1 and switches the Snap module (off by default); `--edges a,b,c,d,e` sets the five edge frequencies in Hz that the modules share (Woof runs from the first to the second, Tub from the second to the third, and so on; each edge must lie within its limits, which `--help` lists); `--threshold` takes dBFS (-60 to 0; at -60 De-Honk always acts); `--lookahead` takes milliseconds, `--trim` takes dB, and `--solo-honk`, `--diff` and `--bypass` are switches. Anything left out takes the plug-in's default. `--block N` sets the block size (512 by default). For more than two channels, `--layout 5.1`, `7.1`, `5.1.4` or `7.1.4` names the speakers in WAV order (L R C LFE, then the surrounds, then the heights), so the LFE is passed through and the Threshold reads the stereo fold-down; `--lfe N` marks channel N alone as the LFE. Without either, no channel is an LFE and channels 0 and 1 are taken as left and right. `--set name=value` overrides one of the internal tuning constants by its name in `dehonk::Tuning` and can be repeated; `--print-tuning` shows the values in use.

`--metrics file.csv` writes two kinds of row under one header, so files can be joined. A `band` row is one analysis band: its centre, the module whose range holds it and whether that module is on, the input and output levels in a 1/12-octave band around it over the whole file, the change, and the mean cut, largest cut and percentage of time the cut was above 1 dB. A `module` row is one module: the level change over its whole range, and the mean and largest of its deepest notch over time and the percentage of time that notch was deeper than 1 dB (from the core's `moduleCutDb`). A `click` row is the Snap module: the level change from 1.8 to 4 kHz (Snap's band, `clickLowHz` to `clickHighHz`), the mean and largest of its cut over time and the percentage of time it was above 1 dB, and in two columns only it fills, the percentage of time above 3 dB and the number of separate events (runs of frames above 1 dB). The levels come from the harness's own FFT analysis of the audio, not from the core, so they check the core rather than repeat what it says about itself. The cut statistics come from the core's display frames.

Snap's figure in a display frame (`snapCutDb`) is the deepest cut it made since the core's previous frame, and the core writes a frame at every detector tick (48 samples, 1 ms, at 48 kHz). Reading the frame once per block of 512 would see one tick in about eleven and miss most of what Snap did, so with `--snap 1` `dehonk_render` processes each block in pieces of 4 samples and reads every frame. The audio is the same either way (`block_size_invariance` checks that).

`--frames file.csv` writes the display frames over time: the time, the deepest notch, the programme level the threshold is compared with, how far above the threshold it is (0 to 1), the deepest notch in each of the four modules, Snap's cut (`cut_click`), how much of the cut the impact guard is holding back (`guard`, 0 to 1), and the cut in every band. `--frame-levels` adds every band's input level as the core measures it. With `--block 8` at 48 kHz there is a frame at every detector tick (every 48 samples). `--help` prints the plug-in's default for every parameter.

`--notch-log file.csv` writes one row per notch: when it opened and closed, the band's centre, its note name and how many cents the band centre is from equal temperament at A = 440 Hz (the bands sit on semitones, so this is close to zero), its deepest cut, the rank of its note's pitch class in the core's key profile (`DisplayFrame::pitchClass`, averaged over `Tuning::keySeconds`, 8 s) at the moment it opened, 1 being the strongest of the twelve, and the module whose range holds it. A notch opens when the band's cut rises above 1 dB and closes once the cut has stayed under 0.5 dB for 100 ms; `close_s` is when it went under 0.5 dB for good. A cut that wavers around 1 dB, or dips briefly, is one notch, not several. The rank is left empty for a notch that opened before `keySeconds` had passed, while the profile was still filling (an empty profile would otherwise rank C first). With `--notch-log` every frame the core writes is read (as with `--snap 1`), so open and close times are good to a detector tick (1 ms) and a notch shorter than a block is not missed; the `--frames` file still gets one frame per block unless `--snap 1` is given.

`--labels file.csv` reads marked moments in the mix: one `time_seconds,kind` row each, with kind one of `impact`, `tonal`, `dialogue_start`, `dialogue_end`, `music_start` and `music_end` (a header line, blank lines, lines starting with `#` and anything after a third comma are ignored). With `--metrics` as well, the metrics file gains rows in extra columns at the end of the same header:

- an `impact` row per marked impact with SPEC 13.2's figures, input against output, in the band from 110 to 400 Hz (the harness's own 4th-order Butterworth high-pass and low-pass): **Body**, the change in energy over the 1.5 s after the onset; **Tail**, the band's decay time before and after, and the change in percent. It is read from a smooth curve rather than from the moment an envelope crosses a level (with several close modes beating, that crossing jumps as the beat lobes pass the line, and the input's own figure moved by 15 to 38% for a 1 dB change in the level): the band's power, less the mean power it had from 400 to 30 ms before the onset (what is underneath), is integrated backwards from the end of the window (Schroeder integration), a least-squares line is fitted to that curve from 5 dB down to 25 dB down, and Tail is the time the line takes to fall 20 dB. In a full mix the material underneath often sits close to the impact in this band, so the curve is only used while the band's 20 ms RMS envelope stays 6 dB above that level, and the fit stops higher up; the span fitted (the same for input and output) is in `tail_fall_db`, and a span under 8 dB, or a curve that does not fall (the material underneath getting louder during the tail), leaves the tail cells blank. The window ends at the next marked impact or after 2.4 s. **Front**, the change in the band's largest sample in the first 30 ms. It also lists the bands that had a notch deeper than 1 dB during the 1.5 s, with their deepest cut;
- a `dialogue` or `music` row per stretch between a `_start` and the next `_end` (or the end of the file): the level in 110 to 400 Hz in and out and the change, and the mean and largest of the deepest cut from 110 to 400 Hz in each display frame.

Front is measured at the Attack of the render; run again with `--speed 0` and `--speed 1` for the other settings.

Each render also prints one line with the level change below the lowest module that is on, across the modules that are on, and above the highest, followed by the mean and largest notch in each module that is on, and with Snap on, its mean and largest cut, the share of time above 3 dB and the number of events.

## Rendering the corpus

Session audio goes under `dehonk/Tests/corpus/`, which is ignored by git along with `dehonk/Tests/build/`. Put the dry files in `corpus/dry/`, in any folder layout, and run:

```
python3 dehonk/Tests/run_corpus.py
```

Each file is rendered to the same relative path under `corpus/out/`, its metrics go beside it, and all the metrics are joined into `corpus/out/metrics.csv` with the file's path as the first column. The module rows alone are also gathered into `corpus/out/modules.csv`. `--in` and `--out` choose other folders, `--frames` keeps each file's display frames too, `--snap` switches the Snap module on for every file (the click rows go into `modules.csv` with the module rows), and anything after `--` is passed to `dehonk_render` for every file, for example `python3 dehonk/Tests/run_corpus.py -- --bark 1 --threshold -20` or `-- --edges 60,120,220,400,1500 --set maxCutDb=6`, or `-- --tub 0 --fog 0 --snap 1` for Snap alone. The script uses only the Python standard library.

## Tools for real mixes

The two Python scripts in `tools/` use only the standard library and call `dehonk_render`.

`dehonk_realmix` takes the measurements that the generated signals cannot stand in for, each on a stereo mix (and, but for `diff`, its dialogue stem), and prints one line per case. Nothing in it passes or fails. `dehonk_realmix key mix.wav dx.wav [other_dx.wav]` attacks the dialogue sidechain: the key late, early, hot, quiet, the whole mix, the mix without its dialogue, upside down and (with a fourth file) another mix's stem, and for each the cut left in the dialogue's bands, the cut kept elsewhere, the gain the key was taken at, how surely it was found (`DisplayFrame::keyMatch`) and how much of the time it was flagged (`keyOver`). `surround` lays the same stems out as 5.1 with the dialogue in the centre and shows what Linked, Grouped and Unlinked leave of each channel's cut. `snap` counts how often and how far Snap cuts in 20 ms windows from 1.8 to 3.5 kHz that are mostly dialogue, with and without the key. `diff mix.wav` measures Compare's level match against the treated output over 3 s and 0.4 s windows, and how fast the gain Compare applies moves, at three averaging times. `tools/realmix_library.sh key|surround|snap|diff [pattern]` runs one of them over the sets in `corpus/library/sets.txt` whose path matches the pattern. The figures in SPEC 13.18 come from these.

`dehonk_dialogue mix.wav dx.wav` measures the dialogue sidechain on a mix and the dialogue stem it was made with (the first two channels of each). It renders the mix twice at the same settings, without a key and with the stem as the key and Dialogue Key on, and the stem once on its own to read its level per band through the core's band bank. Every band of every frame inside a range that is switched on is then sorted by how the stem stands against the mix there, both read from the unkeyed renders, so the sorting uses nothing the dialogue logic works out: the dialogue's (the stem within 3 dB of the mix), not dialogue (12 dB or more under it), or mixed. It prints the mean cut of each kind without and with the key, the same over the bands where a cut was open (0.5 dB or more) without the key, and the trim the core gave the key. `--threshold`, `--all-ranges`, `--depth` and `--amount` set the plug-in; `--key-gain dB` sends the stem up or down, `--key-mono-sum` adds its two channels into a mono key (6 dB up for a voice in the middle, as a stereo stem arrives at a mono key input); `--csv` prints one line of figures; `--set name=value` changes a tuning constant. `tools/dialogue_library.sh [options]` runs it with `--csv` over every set in `corpus/library/sets.txt` (tab separated: mix, dialogue stem, anything else). The figures in SPEC 13.17 come from it.

`tools/find_impacts.py mix.wav -o labels.csv` proposes impact onsets: moments where the broadband short-term level (10 ms RMS every 5 ms, all channels) jumps by at least 8 dB within 30 ms and lands within 6 dB of the loudest short-term level in the file, at least 1.5 s apart, strongest first, up to 20, each refined to about a millisecond (on the ten synthetic impacts it lands within 6 ms of the true onsets). It writes a labels file in the format above. **It is a starting point for a person to correct, not a set of labels**: it cannot tell an impact from a loud entry in the music, it misses impacts that rise slowly or land under something louder, and Front, measured over the first 30 ms, depends on the onset being right. Listen through, move, delete and add, then keep the result in `corpus/labels/<mix name>.csv`. It reads 16, 24 and 32-bit PCM and 32 and 64-bit float WAV with any number of channels (its own reader; RF64 too).

`tools/corpus_report.py [folder]` runs the section 13 measurements over every WAV directly in a folder (default `~/Desktop/honkymixes`; subfolders are not searched, and a file that cannot be read is skipped with a message). For each mix it takes `corpus/labels/<name>.csv` if there is one, otherwise it runs `find_impacts` and writes the proposal to `corpus/report/labels/<name>.csv`. It renders once with the threshold at -60 dBFS to read the programme level the core measures, sets the threshold 8 dB below that level's 85th percentile so the busy moments are above it, and renders again at the plug-in's defaults with that threshold, writing `<name>.metrics.csv` (with the labelled rows), `<name>.notches.csv` and `<name>.frames.csv` into `corpus/report/`. It then writes `summary.csv` and `summary.txt` with, per mix: Body, Tail and Front worst and median over its impacts (and how many tails were measurable), how many notches opened (and how many opened before the key profile had filled, which are left out of the shares), the share of the rest on the three strongest pitch classes and on ranks 4 to 12, the mean deepest cut from 110 to 400 Hz inside and outside the busy moments (programme level above the threshold), and the cut on any marked dialogue. The renders themselves are deleted unless `--keep-renders` is given, and anything after `--` is passed to `dehonk_render`. `corpus/` is ignored by git: session audio and everything made from it stays out of the repository.

## The tests

Levels in the table are measured by the harness's own analysis (Welch-averaged FFT, in 1/12-octave bands around each analysis band centre unless stated), after the first second of each signal so the detector has settled. Cut figures come from the core's display frames.

Most tests run with Threshold at -60 dBFS, where De-Honk always acts. At the default threshold most test signals would be below it and the detector would barely run, so a test such as `transparency_pink` would pass without judging anything. The threshold itself is tested separately. Other parameters are at the plug-in's defaults unless stated, which means Tub and Fog on (110 to 400 Hz) and Woof and Bark off.

Several tests use the same kind of signal: a bass-heavy bed (pink noise with everything below 100 Hz raised by 12 dB) with narrow noise bands peaking 8 dB above it (raised cosine, a sixth of an octave wide at half height), at -12 dBFS RMS. It is called "the peaks signal" below.

Three tests look at notches over time. They render with 8-sample blocks so there is a display frame at every detector tick. `notch_count` judges by the rule in its row below. A notch that has to make room is told from one that is letting go in its own time by how fast it falls: a notch over its module's number is let go at the attack rate (a time constant of about 15 ms at default Attack), anything else at the Release. `notch_dwell` goes by open and closed: a notch opens when its cut rises above 1 dB and closes once it has been under 0.5 dB for 100 ms, as `--notch-log` has it. When a peak moves to a band nearby, the notch that was on it lets go at the Release and the one taking over grows only as it does, so for a while two bands closer than the spacing are open together and add up to what one notch was asked for; the tests count such a group as one notch.

The Snap tests (SPEC section 12.8) run with the four notch modules off unless stated, so only Snap acts. Their signals are pink noise at -22 dBFS RMS with bursts every half second: Hann-windowed sine bursts at peak 0.5 for clicks, white noise with a 1.5 ms decay (6 ms long) for broadband hits, white noise with a 30 ms decay (150 ms long) for snare-like hits, and a 60 Hz sine falling from 150 Hz, with a 1 ms noise tick, for kick-like hits. "Band peak" is the largest sample of the signal through the harness's own band-pass (4th-order Butterworth high-pass at 1.8 kHz and low-pass at 4 kHz) from 8 ms before each burst to 8 ms after it, output against input, averaged over the bursts after the first 0.4 s. Snap's own figures come from `snapCutDb` in the display frames, read at every frame as described above.

The last column says what broken behaviour each test is there to catch. Where a wrong tuning constant shows it, the setting that makes the test fail is given (`dehonk_tests --only name --set ...`); each was run.

| Test | What it checks | Pass limit | Fails if |
|---|---|---|---|
| `null_depth_zero` | At Depth 0 the output equals the input delayed by the reported latency, for pink noise and a music-like signal, mono and stereo, lookahead off and 10 ms, threshold -60. Each case is also rendered at the default Depth to show the signal is one the core acts on. | Residual below -100 dB relative to the input at Depth 0; at the default Depth, residual above -60 dB and a cut above 0.5 dB | anything is changed at Depth 0, or the dry path is not latency-matched |

`automation_clicks` uses two measurements. The main one looks above 6 kHz, where De-Honk does nothing, so the output there must be the input times a slowly changing gain. Each 10 ms window of the output is fitted from the input, the input times time, and the input's derivative and derivative times time (the last two absorb the small phase shift from the skirts of the notches). What the fit cannot explain is a click or zipper noise, and it is reported relative to the output's energy in that window. A discontinuity in a filter's state or gain spreads energy across the whole spectrum, so it shows up here even when it is far too small to see in the waveform. The second measurement is the one the brief asked for: in each 10 ms window, the largest sample-to-sample jump in the output against the largest in the input times the highest trim gain requested within 50 ms. Cuts and mix cannot make the waveform's steps steeper except through small phase changes, so 1.5 dB is allowed for those. It only catches gross jumps, because the pink noise's own steps are large.

The harness works out which module a band belongs to from the edges, as `DeHonkCore.h` documents them (module m spans edge m to edge m+1, each edge clamped to its limits). The core does not expose its own band-to-module map.

Snap is only checked on made-up signals here. Whether what it catches on real mixes are the pops meant needs listening, with `dehonk_render --snap 1` and `run_corpus.py --snap`.

## What is not covered here

The corpus measurements in section 7 of the spec (gain reduction on clean and honky mixes, dialogue stems, generator pairs, and listening) need session audio and are done with `dehonk_render` and `run_corpus.py`, not with `dehonk_tests`. Host checks are done in the hosts.
