# RBass measurement

This folder measures what Waves RBass adds to real material across its settings, before any De-Honk DSP is written (dehonk/SPEC.md, sections 7 and 8, stage 1). It renders audio through the real RBass plug-in using Spotify's pedalboard and compares each render with the dry file. Nothing here imitates RBass: if RBass cannot be loaded, the script stops and reports the exact error.

It has to run on a Mac (or a Windows machine) with Waves RBass installed and licensed, because RBass lives inside the Waves shell (WaveShell*.vst3 or WaveShell*.component), which is a native macOS or Windows binary. It will not load in Linux.

## Setting up

Use Python 3.10 or later. Create a virtual environment outside the repository and install the pinned packages: `python3 -m venv ~/.venvs/dehonk-measure`, `source ~/.venvs/dehonk-measure/bin/activate`, then `pip install -r requirements.txt` from this folder.

Put the dry material into `dehonk/Tests/corpus/dry/`. The whole of `dehonk/Tests/corpus/` is git-ignored, because it holds client audio and the renders made from it. The layout is `sources/` for single sounds (sub drops, booms, impacts, low brass, synth bass), `stems/` for full effects stems, `mixes/<name>/bass.wav` and `mixes/<name>/rest.wav` for a mix split into the part that gets RBass and everything else, and `clean/` for material that never had an enhancer. WAV, AIFF and FLAC are read. Files with more than two channels are skipped and listed in `results/skipped.csv`.

Named settings used in real sessions can be added as `dehonk/Tests/corpus/settings.json`. Run step 1 first so you can see the parameter keys and their value text in `results/rbass_parameters.json`. The file is a list of settings, each with a name and the parameter values to set, keyed by the parameter's key or its name. A value is given as RBass shows it (for example `"60"` or `60` for a frequency in Hz), or as `{"raw": 0.35}` for the plug-in's normalised 0 to 1 value. Parameters that are not listed stay at their defaults. For example: `[{"name": "Booms default", "params": {"frequency": 60, "intensity": 50, "original_bass": true}}]`.

## Running it

`python3 measure_rbass.py all` runs every step in order and stops after step 1 if RBass does not load. Steps can also be named, for example `step2 render analyse`; they always run in that order and in one process. Loading RBass takes several minutes, because the VST3 shell exposes about 130 empty MIDI controller parameters alongside RBass's own and pedalboard probes each one, so it is quicker to run steps together than one at a time. Every step except `analyse` loads RBass first.

Step 1 finds the Waves shell in the standard plug-in folders (or the path given with `--shell`), lists every plug-in in it, and loads the RBass mono and stereo components by name. Each WaveShell only hosts the plug-ins built for its version, so the script first reads the installed RBass bundle (`/Applications/Waves/Plug-Ins V*/RBass.bundle/Contents/Info.xml`) to find which shell version it belongs to, then loads that one shell of each format and no other. The rest stay installed and untouched; loading two versions into one process clashes their classes. The shells it skipped are listed in the load report. It tries the VST3 shell first and the Audio Unit shell if the VST3 one fails. macOS prints a long run of `objc[...] Class ... is implemented in both` warnings while the Waves shell loads, because the shell pulls in every installed Waves library; they can be hidden by running the script with `2> >(grep -v '^objc\[' >&2)` on the end. The outcome of every attempt, with the full error text, goes to `results/rbass_load_report.json`. When both components load, every parameter's key, name, range, default, units and possible values go to `results/rbass_parameters.json`, along with the shell's version. The script then works out which parameters are the frequency, intensity, original bass switch and output gain by their names, and prints what it chose. If it cannot tell, it says so and you pass the key with `--param-frequency`, `--param-intensity` or `--param-original-bass`.

Step 2 checks the host. pedalboard already removes the latency the plug-in reports; the script measures what is left with an impulse, cross-checks it with a noise burst, and does this at the least-effect setting and at full intensity with the original bass out. It then removes that residual delay from every render so dry and wet line up to the sample. It also renders pink noise at the least-effect setting (minimum intensity, original bass in, everything else at default) and reports how far it is from the dry signal in dB. The results go to `results/host_check.json`.

The render step generates the test signals (sines at 30, 40, 50, 60, 80 and 100 Hz and a log sweep from 20 to 200 Hz, each at -18 and -6 dBFS peak, 5 seconds, 48 kHz) into `corpus/generated/`, then renders every test signal and every file in `sources/`, `stems/` and `mixes/` through RBass at the least-effect setting, over the grid, and at each named setting. The grid is six frequency values and five intensity values spread across each parameter's range, with the original bass in and out, and output gain left at its default. Mono files use the mono component and stereo files the stereo one. For a mix, only `bass.wav` is processed and the result is summed with `rest.wav`; the dry reference is `bass.wav` plus `rest.wav`, written as `dry_sum.wav` next to the renders. Files in `clean/` are not processed. Every render is 32-bit float at the file's own sample rate, with no resampling, normalising or limiting, and goes to `corpus/wet/<category>/<item>/<setting>.wav`. Each render's peak is recorded and anything over 0 dBFS is flagged. RBass itself clips its output at 0 dBFS, so the manifest, summary and harmonics tables also count the samples at or above 0.999 in each render; where that count is not zero, the extra harmonics include clipping distortion as well as what RBass generates.

`results/manifest.csv` has one row per render: the dry and wet paths, the setting, the text and raw value of every RBass parameter, sample rate, channels, length, the latency correction applied, and the peak. `results/null_test.csv` compares each least-effect render with its dry file, giving the residual in dB below the dry level, the overall level change, and the change in each summary range.

Corpus file names are client material and the results folder is committed to a public repository, so by default the committed results name corpus files by category and number (`source01`, `stem03`, `mix02`). The real names are in `corpus/name_map.csv` and a manifest with the real paths is in `corpus/manifest_private.csv`, both git-ignored. `--keep-names` uses the real names everywhere instead.

The analyse step reads the manifest and compares each dry and wet pair through a bank of 1/12-octave band-pass filters from 40 Hz to 2.5 kHz (sixth-order Butterworth per band, with bands below 250 Hz run on a 1.5 kHz copy of the signal and the rest on an 8 kHz copy). Levels are mean power in dB relative to a full-scale sine, so a 0 dBFS sine reads 0 dB in its band. `results/bands_longterm.csv` has one row per pair with the dry, wet and wet-minus-dry level for every band, and one dry-only row for each clean file. The same levels per 10 ms frame are saved for each pair in `corpus/wet/analysis/` as .npz files (`band_hz`, `frame_s`, `dry_db`, `wet_db`, stored as 16-bit floats to keep the size down). `results/summary.csv` gives, per pair, the dry level, wet level and change below 100 Hz and in 100 to 150, 150 to 250, 250 to 500 and 500 to 1000 Hz; these ranges come from a single FFT of the whole file rather than the band bank, because the bank does not reach below 40 Hz. `results/harmonics.csv` gives, for every sine test signal, the dry and wet level of harmonics 1 to 10, measured over the steady middle four seconds.

The plots are in `results/plots/`, one image per source and original bass setting, with a panel per frequency value and a line per intensity value showing wet minus dry per band. For the test signals the plots show the wet level per band relative to the signal's input level instead, because a sine or a sweep has almost nothing in most bands and wet minus dry there only measures the dry file's noise floor. `results/heatmap_added_level.png` shows the added level per band for every setting, averaged over the corpus files, and `results/heatmap_added_level_test_signals.png` does the same over the test signals.

## Useful options

`--only <text>` limits the run to items whose name contains the text. `--force` re-renders wet files that already exist; without it, existing renders are reused. `--format vst3` or `--format au` forces one plug-in format. `--buffer-size` sets the block size used for rendering (512 by default). `--corpus` and `--results` point at other folders.
